## Inspiration

DataHub knows a dataset's lineage, schema, and ownership. Git knows which files change together, which ones churn, and which ones keep breaking. Nobody joins them — so an agent working on a data pipeline sees the catalog or the repository, never both at once.

The join sounds trivial. A dbt model is a file. Walk from the dataset URN to the model to the file, attach whatever the repository knows about it, done.

We tried it. It returned **zero rows** — silently, with no error.

dbt reports `original_file_path` relative to the **dbt project root**. Repository evidence is keyed relative to the **git root**. The moment a dbt project lives in a subdirectory — `dbt/`, the common real-world layout — the two path representations differ by exactly that prefix, every lookup misses, and the join hands back an empty result that looks indistinguishable from "this dataset has no interesting history."

A silent zero is the worst possible failure shape for a metadata join. It doesn't alert anyone. It just quietly makes the integration useless. That is the problem this project exists to close.

## What it does

Resolves a DataHub dataset URN to the source file that produces it, then attaches repository behavioral evidence to that file:

```
DataHub dataset URN
  -> dbt manifest node        reconstructs database.schema.alias to match back
  -> original_file_path       every node accounted for, never silently dropped
  -> repo-root-relative key   the normalization that makes the join actually work
  -> workspace.json evidence  co-change, churn, fragility
```

Two properties mattered more to us than feature count.

**Nothing vanishes.** Extraction reports every dbt node as *kept*, *excluded*, or *dropped*, under an invariant anyone can check:

```
kept + dropped + excluded == total
```

A node that is dataset-bearing but has no resolvable source file produces a warning that names it. A node excluded by policy (a dbt test is not a dataset) is counted, not hidden. Measured against our frozen proof corpus, the obvious implementation silently discards **23 of 28 nodes**. Ours discards none without saying so.

**Every claim is pinned to evidence.** The proof corpus is frozen at an immutable commit. Fixtures are regenerated by a script that *refuses to run* against an unpinned checkout. Every coverage number in this submission is reproducible from that commit with one command, on any machine, with no warehouse and no credentials.

## How we built it

**Proof corpus, frozen.** `dbt-labs/jaffle_shop_duckdb` at commit `36bde6cba69d962b83be1d52fc65a0dce1cb4ebb`. It runs on DuckDB, so a judge can rebuild the exact manifest locally — no Snowflake, no Postgres, no secrets. We chose reproducibility over history depth deliberately: a proof that can't be independently re-run is worth less than a shallow one that can.

**Node-type coverage, verified rather than assumed.** The whole join rests on `original_file_path` being populated. We checked every dbt node type instead of assuming SQL-model behavior generalizes. Result at dbt 1.12.0: models (SQL *and* Python), seeds, snapshots, tests, and sources all populate it — **zero nulls**.

Snapshots, Python models, and sources don't exist in the corpus, so rather than extrapolate we built a minimal probe project that instantiates exactly those three and verified them there. Two sources of evidence, each labelled with which one backs which claim.

**Provenance, per file.** The path-normalization adapter is pre-existing work. It was adopted into this repository with a per-file audit trail: four of five files are byte-identical to their pre-migration origin, the fifth carries a single documented type-only deviation, and a 35-check parity harness runs against the original to prove behavior is unchanged. The harness reverses the documented deviation and re-compares, so "type-only" is verified rather than asserted.

## Challenges we ran into

**The silent zero.** Reproduced cleanly: 5/5 models matched with the dbt project at the repository root, **0/5 when nested**. Fixed by deriving the project prefix from wherever `dbt_project.yml` actually lives, and enumerating *every* dbt project in a repository rather than assuming a single knowable path — real repositories hold more than one.

**Silent drops hiding behind a passing test suite.** Filtering to `resource_type === "model"` with a truthy `original_file_path` looks correct and is not. On the corpus it throws away 23 of 28 nodes. On the node-type probe it throws away exactly the snapshot and the seed — precisely the node types we'd just finished verifying. Nothing failed. Nothing warned. Both filters now report.

**A type stub masking a real compile error.** The adapter only typechecked in its original home because an ambient declaration shadowed `node:fs`. Against real `@types/node` it produced four errors in code that had been shipping. We did not carry the shim forward — it would have masked type errors across the entire application — and filed the finding upstream.

**Assumptions in our own spec.** Our internal notes said dbt sources use a different path field from nodes. They don't; they use the same `original_file_path`. But a source's path points at the *YAML that declares it*, not a model file — so evidence for a source isn't separable from the other sources sharing that file. Worth knowing before promising per-source scores.

## Accomplishments that we're proud of

Every number here is reproducible from a pinned commit by anyone who clones the repository. Not "we measured this once" — the corpus is frozen, the fixture generator refuses unpinned checkouts, and the coverage claim ships with pasted command output rather than prose.

We also documented what our proof corpus **cannot** show. Its dbt project sits at the repository root, so it never exercises the nested-project normalization that is the entire reason the adapter exists. That case is covered by an explicit perturbation test instead, and we say so. A stated limitation reads better to a careful reviewer than a number that quietly doesn't support the claim it's attached to.

## What we learned

dbt's manifest is more consistent than its reputation suggests. `original_file_path` is populated for every node type we tested, including snapshots and Python models. **The risk was never the null. It was the filter above the null** — and no test caught it, because dropping data silently is indistinguishable from having less data.

The broader lesson: for metadata integrations, the dangerous failure isn't the crash. It's the empty result that looks like an answer.

## What's next

Publish the producer CLI so the evidence side of the join can be generated for any repository rather than reconstructed. Wire the DataHub MCP read path so resolution runs against a live instance. Extend to a deeper-history pipeline repository — co-change signal from 92 commits is illustrative, not statistical.

The improvement we'd most like to see in DataHub itself: **have dbt ingestion preserve `original_file_path` and the dbt `unique_id` on the dataset entity.** This entire project exists because the source file location isn't retrievable from DataHub — it requires re-reading `manifest.json` out of band and reconstructing `database.schema.alias` to match back. Carried as a dataset property or custom aspect, any consumer wanting to connect a dataset to the code that produces it would get it in one hop, and the path normalization here would become unnecessary for DataHub consumers entirely.
